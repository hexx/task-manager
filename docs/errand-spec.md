# お出かけ（Errand）タブ 仕様（v1）

> ステータス: 確定（grill-with-docs セッション合意済み）
> 用語の定義は [CONTEXT.md](../CONTEXT.md) を参照。

## 1. 背景・目的

買い物や外出先でやる用事（スーパーでの買い物、銀行・郵便局への立ち寄りなど）は、このアプリで最も利用頻度の高い用途であり、従来 Task として管理している。しかし既存の Task 行 UI には期限・フォルダ選択など買い物用途では使わない機能が多く、外出中の片手操作には重い。購入・実行すれば消費される「今日の用事」を、**Tasks と独立した「お出かけ」タブ**で軽快に扱えるようにする。

Checklists や Twitter と同じく独立したタブとして扱うが、**新エンティティは作らない**。Task に `errand` フラグを追加し、タブはその絞り込み表示とする。

## 2. 概念モデル

| 概念 | 説明 |
|---|---|
| **Errand** | 外出先で行う一度きりの用事。買い物を含む。Task の一種で、`errand` フラグ（true）により識別される。Folder も Deadline も持たない |
| **お出かけタブ** | `errand = true` の Task のみを表示する絞り込みビュー |

- Errand は**使い切り**（Task と同じ性質）。完了しても自動削除はされず、既存の完了表示パターンに従う。
- Errand は Task タブの「すべて」「未分類」から**除外**される（既存の「すべて = 全 Task」から意味論が変わる。§3.5 および [CONTEXT.md](../CONTEXT.md) の All / Unclassified の定義参照）。

## 3. 機能要件

### 3.1 タブの配置とデフォルト

- タブの並び: `Tasks | お出かけ | Checklists | Twitter`（Tasks の直後）
- アプリ起動時のデフォルト選択は **Tasks のまま**（変更しない）

### 3.2 タスク作成

- フォームは**タイトルのみ**。期限・フォルダ指定の UI は出さない
- 作成した Task は自動的に `errand = true` として作成する（`POST /api/tasks` に `errand: true` を送る）
- タイトルは trim 必須、空は 400（既存パターン準拠）

### 3.3 タスク行

- 表示は **チェックボックス + タイトル + 削除ボタン** のみ
  - 期限表示・フォルダ選択セレクトは出さない
  - タイトル編集は既存 Task 同様にない
- 完了トグルは既存の楽観的更新パターン（[docs/mobile-show-completed-spec.md](mobile-show-completed-spec.md) v3 第5節）を踏襲する
- 削除は確認ダイアログなし（既存 Task と同じ）

### 3.4 完了の表示

- デスクトップ: 「完了を隠す/表示」ボタン。既定は**非表示**（既存 Tasks ビューと同じ）
- モバイル: 一覧には未完 Task のみを表示し、完了 Task は末尾の開閉セクション（既存 v3 パターン踏襲）

### 3.5 Task タブ側の変化

| 絞り込み | 条件 |
|---|---|
| すべて | `!errand`（Errand を除く全 Task） |
| 未分類 | `!errand && folderId === null` |
| フォルダ | `folderId === id`（Errand は Folder を持てないため実質変化なし） |

- 既存の Task 作成フォーム・一覧 UI には変化なし（フラグなし Task は従来どおり）

### 3.6 既存 Task の移動

- v1 では既存 Task → Errand への移行 UI は**作らない**（削除して作り直しで対応）
- `PATCH /api/tasks/:id` で errand を変更する経路も**設けない**
- 逆方向（Errand → 通常 Task）も同様に不可

## 4. データモデル

- マイグレーション `migrations/0003_add_task_errand.sql` を新設:

```sql
ALTER TABLE tasks ADD COLUMN errand INTEGER NOT NULL DEFAULT 0;
```

- `schema.sql` の tasks テーブル定義にも反映する（新規環境向け）
- `Task` 型（`src/shared/task.ts`）に `errand: boolean` を追加。store の `rowToTask` / `cloneTask` / メモリ実装にも反映

## 5. API

| メソッド | パス | 変更 |
|---|---|---|
| `GET` | `/api/tasks` | 変更なし（全件返却。絞り込みはクライアント側＝既存流儀） |
| `POST` | `/api/tasks` | `{ title, errand?: boolean }` を受け付ける。省略時は false |
| `PATCH` | `/api/tasks/:id` | 変更なし（errand の変更は受け付けない） |
| `DELETE` | `/api/tasks/:id` | 変更なし |

## 6. 画面構成

- お出かけタブはデスクトップ・モバイル共通でフラットな1カラム（Folder サイドバー・フォルダピッカーシートは出さない）
- 上部に作成フォーム（タイトルのみ）、その下にタスク行の一覧
- デスクトップ: 完了表示トグル（§3.4）/ モバイル: 完了開閉セクション（§3.4）
- タスク 0 件の場合は既存の空状態表示に準拠

## 7. 対象外（v1 ではやらない）

- 既存 Task → Errand への移行 UI、および逆変換
- Errand への Deadline・Folder 設定
- アイテムの数量・金額・「買う/やる」種別・優先度
- 手動並べ替え
- 完了 Task の自動削除・アーカイブ
- Checklist（忘れものリスト）との連携
- 単価・合計・レシート管理等の買い物特化機能

## 8. 決定経緯（なぜ新エンティティではなく Task フラグか）

- 候補: (a) 新エンティティ「お出かけリスト」 (b) Task への `errand` フラグ (c) Checklist 流用
- ユーザーの運用は既に「Task として登録」であり、「今日の1回で消費する」という Task の性質と一致する。新エンティティはデータ形状が Task と重複するわりに UI は軽いという不均衡になり、Checklist は「リセットして使い回す」前提が合わない
- Task フラグならデータモデル・API の変更が最小で、UI の差（軽い行・フォルダ/期限の非表示）だけを新タブで表現できる
- 「すべて = 全 Task」の意味論は変わるが、CONTEXT.md の All / Unclassified の定義更新で吸収する。将来独立エンティティが必要になっても、フラグを残したままビューを差し替えればよい
